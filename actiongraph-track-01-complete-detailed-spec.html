1. Executive summary and winning thesis

ActionGraph is a graph-native safety controller for agents that propose changes across connected systems. Its purpose is not to make an agent sound careful. Its purpose is to evaluate whether a proposed plan violates explicit safety invariants in the current dependency graph, explain the exact path behind the decision, control the execution of approved actions, and verify observed state afterward.

The winning thesis is to show a visible before/after: a naïve automation would disable a departing contractor and accidentally orphan a critical service. ActionGraph traverses FalkorDB, detects the dependency, blocks the unsafe plan, and provides a safe sequence. When a simulated step times out, it reads back state and represents the outcome honestly instead of claiming rollback or blindly retrying.

Primary promise

Prove before act

Every high-impact plan is evaluated against graph-derived dependencies and deterministic invariants.

Technical proof

Graph changes verdict

Remove a critical ownership edge and the same plan changes from approved to blocked.

Reliability proof

Verify after act

Success means observed postconditions hold, not merely that a tool returned HTTP 200.

Responsible behavior

Uncertainty is explicit

Partial failures, unknown outcomes, and irreversible steps are never described as safely rolled back without evidence.

What judges should remember

  1. The problem is understandable: an action can harm something several relationships away.
  2. FalkorDB is doing real work: graph paths and connected ownership/dependency state determine the verdict.
  3. The safety decision is deterministic and reproducible, not an LLM opinion.
  4. The system verifies the resulting state and handles a failure without pretending all actions are reversible.
Core demo in one sentence: “The graph proves this plan would orphan a critical service, so ActionGraph blocks it, shows the path, safely repairs ownership, and verifies the final state.”

Scope principle

Build one exceptionally clear scenario with simulated side effects. Do not build a generic agent platform, real production connectors, or a large collection of shallow features. The strongest submission is one where every technical claim is backed by a visible test.

Definition of done for the hackathon MVP

  • At least one real multi-hop dependency path returned by FalkorDB.
  • A named invariant causes an unsafe plan to be blocked.
  • A safe alternative can pass preflight and run in a mock executor.
  • At least one partial failure is injected and correctly represented.
  • Final status is based on read-back/postcondition verification.

Do not claim universal safety, formal verification of arbitrary actions, guaranteed rollback, production readiness, or a unique category unless you have evidence. Say “a bounded prototype that enforces selected invariants for the supported action types.” Precision makes the pitch more credible.

3. Problem, target user, and job-to-be-done

Problem

Agent systems can call APIs and automate workflows, but action permissions and local tool success do not establish that a multi-step plan is safe in the context of connected resources. Disabling a user, deleting a resource, rotating a credential, or changing a deployment may affect dependent systems several hops away. A model can fail to mention a relationship; a static allow-list can miss context; and a successful API call can leave the overall workflow in a broken state.

Initial customer profile

PersonaJob to be doneFirst useful outcome
Platform/SRE engineerAllow agents to perform bounded operational changes without blind executionPreflight detects a dependency that a naïve run misses
IT operations / identity teamOffboard users without orphaning service ownership or access dependenciesSafe ordered checklist with verified replacement owner
Security/automation engineerEnforce contextual controls around high-impact agent actionsNamed invariant, evidence path, and approval gate
AI product engineerMake tool-using agents auditable and recoverableExecution journal and state verification API

Job statement

When an agent proposes a high-impact change across connected systems, help me understand its blast radius, block it if a required invariant would fail, and prove what state was actually reached—without trusting the model's explanation as the safety authority.

Why start with synthetic offboarding?

  • Judges immediately understand identity deactivation and service ownership.
  • It naturally creates multi-hop graph traversal: identity → owns → service → depends on → resource/credential.
  • It has an obvious invariant: every critical service must have an eligible active owner.
  • It provides a natural safe plan: assign and verify replacement owner before deactivation.
  • It can be demonstrated without touching real identity systems or private company data.

Non-functional requirements

  • Determinism: policy results repeat for the same graph snapshot and plan.
  • Boundedness: graph traversal depth, node count, action count, and request size are capped.
  • Safety: no supported action executes if preflight cannot complete.
  • Auditability: every status transition has a timestamp and reason.
  • Reproducibility: seed data and tests are deterministic.
  • Portability: local setup works with documented environment variables.

Explicit exclusions

In the hackathon MVP, do not connect production accounts, execute arbitrary shell commands, promise general rollback, or let an LLM generate raw Cypher. No multi-cloud connector marketplace, billing, enterprise SSO, or general policy language is required to prove the concept.

5. Signature scenario and demo storyboard

Seed graph

Use a fictional workspace with these relationships: contractor identity id-contractor-17 owns critical service svc-billing; the service depends on credential-deploy-4; the credential is issued to the contractor; candidate replacement id-engineer-9 exists but is not yet an eligible owner. A criticality label on the service activates the invariant.

Scenario A: unsafe plan

  1. Planner proposes disable_identity(id-contractor-17) and revoke_credential(credential-deploy-4).
  2. ActionGraph traverses ownership and dependency relationships.
  3. The invariant evaluator computes that the critical service would have zero eligible active owners after the proposed changes.
  4. Plan becomes BLOCKED; no executor call is made.
  5. UI shows the exact path and the failing invariant.

Scenario B: safe plan

  1. Proposed plan adds replacement ownership and validates replacement eligibility.
  2. Preflight verifies that the new owner is active and authorized, and that service ownership remains continuous.
  3. Plan enters AWAITING_APPROVAL if the policy requires approval; a simulated human approves.
  4. Executor applies the mock ownership change and verifies it by reading back state.
  5. Only after replacement ownership is verified can the disable step proceed.
  6. Final verification confirms the invariant still holds.

Scenario C: injected partial failure

  1. After replacement ownership succeeds, the identity-disable operation times out.
  2. ActionGraph does not assume the operation failed; it reads the simulated identity state.
  3. If state is active, it can retry safely under an idempotency policy; if the state cannot be determined, it marks the run UNKNOWN and requests review.
  4. UI explains what succeeded, what is unknown, and which invariant is still satisfied or at risk.

6. System architecture and data flow

Component contracts

Impact serviceValidated plan + graph snapshotAffected nodes and pathsRun unbounded traversals

VerifierExpected postconditionsVerified/failed/unknown stateTrust tool response without read-back

Data flow

  1. Authenticate caller and validate the requested action types and target IDs.
  2. Read current graph state and construct a bounded plan impact context.
  3. Compute affected services/resources and evaluate invariants deterministically.
  4. Store the decision, rule IDs, graph paths, and relevant graph version/snapshot identifier.
  5. If blocked, return explanation and a safe alternative suggestion without execution.
  6. If approved, execute one action at a time through the controlled adapter.
  7. After each step, record result and re-read simulated system state.
  8. Check postconditions and invariants; continue, compensate, retry, or request review according to explicit policy.
  9. Export a machine-readable audit report and a human-readable summary.

7. FalkorDB graph model

The schema below is a design proposal. Pick stable IDs, normalize relationship directions, and document the meaning of every property. The graph should model both current connected state and what a proposed action would change. Do not mix hypothetical state with observed state without labels.

LabelPropertiesRelationshipsValidation rules
Workspaceid, name, schema_versionHAS_IDENTITY, HAS_SERVICE, HAS_RESOURCEIDs stable; tenant/workspace selected server-side
Identityid, status, identity_type, eligible_ownerOWNS, ISSUED, CAN_ACCESSOnly active eligible identities count as owners
Serviceid, criticality, statusDEPENDS_ON, OWNED_BY, RUNS_ONCritical service requires at least one eligible owner
Resourceid, resource_type, status, criticalityDEPENDS_ON, MANAGED_BYCannot delete while active critical dependency exists
Credentialid, status, scope, expires_atISSUED_TO, GRANTS_ACCESS_TORevocation policy depends on replacement access and service impact
Invariantid, rule_type, severity, enabledPROTECTS, APPLIES_TORules are code-backed, not arbitrary model expressions
Planid, status, created_at, graph_versionCONTAINS_ACTION, EVALUATED_AGAINSTImmutable identity; status transitions are explicit
Actionid, action_type, target_id, sequence, statusPRECEDES, AFFECTS, REQUIRESAction type and target must be allow-listed
Decisionid, verdict, rule_id, reason_code, created_atEVALUATES, SUPPORTED_BY_PATHDecision has reproducible evidence
ExecutionEventid, idempotency_key, outcome, observed_atRESULT_OF, VERIFIED_BYRetries do not duplicate effects in simulation
Observationid, state_value, observed_at, sourceOBSERVES, CONFIRMSObserved and expected state kept distinct

Relationship conventions

  • (Identity)-[:OWNS]->(Service): identity is an eligible service owner only when its status/policy permits.
  • (Service)-[:DEPENDS_ON]->(Resource): service requires resource for a stated capability.
  • (Credential)-[:GRANTS_ACCESS_TO]->(Resource): credential access relationship.
  • (Plan)-[:CONTAINS_ACTION]->(Action): ordered proposed actions.
  • (Action)-[:AFFECTS]->(Service|Resource|Identity|Credential): resolved target and impact.
  • (Decision)-[:SUPPORTED_BY_PATH]->(EvidenceNode): explicit evidence references; if the client representation of paths differs, store path node IDs and relationship types as a structured record.
  • (ExecutionEvent)-[:RESULT_OF]->(Action), (Observation)-[:CONFIRMS]->(ExecutionEvent): post-action verification.

Separate actual and proposed state

Never mutate the actual graph to pretend a proposed plan has already happened. For MVP, calculate projected effects in application code from validated actions and compare them against the actual graph. If you model projected state as graph nodes/edges, label them with a plan/snapshot ID and ensure every query clearly distinguishes observed state from proposed state.

8. Core graph queries and invariant evaluation

The examples are conceptual Cypher patterns. Confirm exact FalkorDB Cypher support, parameter passing, path return shape, and client API in the version you use. Do not interpolate untrusted strings into query text.

8.1 Find critical services owned by a target identity

MATCH (i:Identity {id: $identity_id})-[:OWNS]->(s:Service)
WHERE s.criticality = 'critical' AND s.status = 'active'
RETURN i.id AS identity_id, s.id AS service_id, s.criticality AS criticality;

This is a starting direct relationship check. The full blast-radius query should traverse relevant dependency relationships to bounded depth and return path evidence. Keep the path output bounded so a large graph cannot overwhelm the API or prompt.

8.2 Illustrative multi-hop impact path

MATCH p = (i:Identity {id: $identity_id})-[:OWNS|DEPENDS_ON|GRANTS_ACCESS_TO|ISSUED_TO*1..4]-(n)
WHERE n:Service OR n:Resource OR n:Credential
RETURN n.id AS affected_id, labels(n) AS labels,
       length(p) AS hops
LIMIT 100;

Implementation caution: variable-length patterns and relationship direction can differ in supported syntax and may return semantically noisy paths. Prefer explicit, allow-listed path patterns for the MVP—for example identity-to-owned-service, service-to-dependency, credential-to-resource. Test that each returned path has a meaningful direction and reason; do not count arbitrary connectivity as impact.

8.3 Deterministic owner invariant

For a proposed plan, calculate each affected critical service's eligible owner set after applying only the plan's validated ownership changes to a projected in-memory view. The invariant is:

for each affected critical service:
    eligible_after = current_eligible_owners(service)
                     - owners_removed_by_plan(service)
                     + owners_added_by_plan(service)
    if len(eligible_after) == 0:
        verdict = BLOCK
        evidence = path_to_service + owner_set + planned_removal

This code-like expression is clearer than asking the LLM to decide. Keep the graph as the source of current owners and dependencies; application code performs a deterministic projection. Document the limits: if your projection engine does not model a class of change, reject or require review rather than assume safety.

8.4 Find dependent resources before deletion

MATCH (s:Service)-[:DEPENDS_ON]->(r:Resource {id: $resource_id})
WHERE s.status = 'active' AND s.criticality = 'critical'
RETURN s.id AS service_id, s.criticality AS criticality
LIMIT 100;

8.5 Query plan/action history

MATCH (p:Plan {id: $plan_id})-[:CONTAINS_ACTION]->(a:Action)
OPTIONAL MATCH (e:ExecutionEvent)-[:RESULT_OF]->(a)
RETURN a.id AS action_id, a.action_type AS action_type,
       a.status AS action_status, e.outcome AS outcome,
       e.observed_at AS observed_at
ORDER BY a.sequence ASC
LIMIT 200;

Required query tests

  • Expected owner path is returned for the seeded scenario.
  • Removing the ownership edge changes the invariant result.
  • Inactive identities do not count as eligible owners.
  • Inactive/non-critical dependencies are not incorrectly elevated to critical impact.
  • Traversal limit is enforced.
  • Unknown target and graph failure cause no execution.

9. Plan lifecycle, execution, and reconciliation

Plan state machine

PROPOSED
  → VALIDATING
  → PREFLIGHTED
      → BLOCKED
      → NEEDS_REVIEW
      → AWAITING_APPROVAL → APPROVED → EXECUTING
                                     → VERIFYING
                                         → VERIFIED
                                         → PARTIAL_FAILURE → RECONCILING
                                         → UNKNOWN → HUMAN_REVIEW
                                         → FAILED (only when failure is established)

Store every transition with plan ID, actor/system component, timestamp, previous state, next state, reason code, and evidence reference. Avoid using one generic failed status for timeouts, partial effects, and confirmed failures.

Plan object

{
  "plan_id": "plan-offboard-001",
  "scenario": "synthetic_identity_offboarding",
  "graph_snapshot": "seed-v1",
  "actions": [
    {
      "action_id": "a1",
      "type": "assign_service_owner",
      "target_id": "svc-billing",
      "params": {"new_owner_id": "id-engineer-9"},
      "preconditions": ["new_owner_is_active", "new_owner_is_eligible"],
      "postconditions": ["new_owner_owns_service"],
      "idempotency_key": "plan-offboard-001:a1"
    },
    {
      "action_id": "a2",
      "type": "disable_identity",
      "target_id": "id-contractor-17",
      "preconditions": ["critical_services_have_eligible_owner"],
      "postconditions": ["identity_status_is_disabled"],
      "idempotency_key": "plan-offboard-001:a2"
    }
  ],
  "requires_approval": true
}

The model may propose a plan shape, but schema validation and allow-lists are authoritative. Ignore or reject unsupported actions and conditions. Never accept arbitrary executable code or raw Cypher in a plan.

Execution algorithm

  1. Acquire a plan execution lock/lease if the implementation supports concurrent requests; otherwise reject simultaneous execution in the MVP.
  2. Check plan status, graph snapshot/version, and approval requirements.
  3. Re-run preflight immediately before the first side effect to reduce stale-state risk.
  4. Execute one action via the mock adapter using idempotency key.
  5. Read back the simulated system state and verify that action's postconditions hold.
  6. Record the observation and action event.
  7. Re-evaluate invariants after each state-changing step.
  8. Continue only if the next step remains valid; otherwise stop and reconcile.
  9. At completion, verify plan-level invariants and emit a report.

Timeout semantics

A timeout means “the caller did not receive a conclusive response,” not “the action failed.” The reconciler must query actual state. If state shows the desired outcome, mark the action executed and verified; if unchanged, retry only if the action is idempotent and preconditions still hold; if state is ambiguous or the readback fails, mark unknown and require review.

Compensation, not magical rollback

For a safe reversible action such as adding an ownership edge in a synthetic graph, a compensation might remove that newly added edge if no later step depends on it. But compensation itself has preconditions and can fail. For irreversible actions, the correct behavior may be stop-and-escalate. Document compensation rules and test them; never claim a generic transaction spans all systems.

11. UI/UX specification

Screen 1 — Plan and verdict

  • Plan ID, requester, target, ordered actions, status, and approval requirement.
  • Large, clear verdict: PASS, BLOCK, or NEEDS REVIEW; never use color alone to communicate status.
  • Invariant name and plain-language reason.
  • Button to inspect evidence path; no execution button when blocked.

Screen 2 — Blast-radius explorer

  • Show the target node and affected services/resources.
  • Show why each node is affected: relationship sequence, depth, criticality, and whether it is direct or transitive.
  • Allow the judge to select a path and inspect node properties.
  • Cap paths and label the traversal limit to avoid suggesting the graph is exhaustive if it is not.

Screen 3 — Execution timeline

  • One row per action with planned, started, response, read-back, and verification states.
  • Display injected failure visibly, including whether actual state was read successfully.
  • Distinguish “API returned success” from “postcondition verified.”

Screen 4 — Invariant report

  • List each invariant, result, affected nodes, evidence path, and evaluation timestamp.
  • Show before/after owner counts and post-action check.
  • Allow exporting a JSON report.

Design guidance

Prefer a small professional interface over a complicated node editor. A graph screenshot is not proof; the interface should show the query-driven path and decision. Seed the demo in a predictable state and add a “reset scenario” action that restores synthetic data.

Benchmark methodology

Use a fixed synthetic scenario suite. Report unsafe-plan block rate, safe-plan false-block rate, invariant evidence coverage, verification accuracy, graph-ablation outcomes, and preflight latency. Include test count, machine/container environment, graph size, and whether model latency is excluded. Never claim broad performance superiority from a handful of handcrafted examples.

Recommended acceptance targets for a prototype

  • 100% of explicitly seeded unsafe scenarios blocked in the test suite.
  • 100% of graph-unavailable preflight cases fail closed.
  • 100% of “verified” labels correspond to the simulated postcondition being true.
  • Every block in the demo includes a named invariant and reproducible evidence path.
  • All duplicate execution and partial failure tests pass.

These are internal acceptance targets for the known synthetic cases, not a claim of general-world safety.

20. Pitch and submission package

60-second pitch

AI agents can change connected systems faster than teams can reason about every dependency. ActionGraph adds a graph-native safety checkpoint before those changes happen. It traverses relationships in FalkorDB, evaluates explicit invariants, and returns the exact evidence path behind a block or approval. In our synthetic offboarding demo, an agent is prevented from disabling the only eligible owner of a critical service. After a replacement owner is verified, the plan runs through a controlled executor, and ActionGraph reads back the actual state. When a step times out, it reconciles instead of pretending rollback is guaranteed. FalkorDB powers the decision itself—not just the visualization.
